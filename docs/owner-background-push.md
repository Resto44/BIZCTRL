# Owner background notifications

Owners opt in on `/notifications`, separately on each device. The device follows the restaurant selected at enrollment; enabling for another restaurant switches that device's subscription. Existing browser subscriptions are never silently assigned to a different user. Sign-out revokes the browser subscription. iOS/iPadOS 16.4+ requires opening the installed Home Screen web app and tapping Enable notifications.

Database AFTER triggers capture inserts, meaningful updates and deletes on business tables with `restaurant_id` or legacy `org_id`. The migration installs triggers on the tables present at migration time; new business tables must add the same trigger. Internal audit logs, transient carts, live locations, counters, notification queues and telemetry are excluded. Record event history is kept for 30 days. The payload contains operation, table label, reference and branch, not the full record or credentials. Notifications can be visible on the lock screen according to device settings.

Events and per-device delivery jobs commit with the business transaction. Only approved owners of the same restaurant receive jobs. Delivery rechecks current membership and device state. Cron polls every 10 seconds, claims up to 40 jobs with SKIP LOCKED, and uses 8 concurrent provider calls. Jobs retry with exponential backoff, at most 8 attempts / 24 hours. Provider 404/410 disables stale devices. A crash after provider acceptance but before status commit may retry: the event ID notification tag replaces that event's previous display. Provider acceptance does not guarantee device presentation; OS settings, Focus, connectivity and browser lifecycle still apply.

`owner-push` uses custom authentication: config exposes only the public VAPID key; subscribe/test verify the user's access token with Auth and check approved owner membership. Dispatch requires a random Vault-only secret. VAPID keys are generated inside the Edge Function once and stored in Vault by a service-role-only RPC. No private keys are bundled or committed. Browser subscription URLs are restricted to known HTTPS push providers, with redirects disabled.

Deployment order: apply the migrations, deploy `supabase/functions/owner-push` with `verify_jwt=false` (custom auth is in the handler), GET `/config` to initialize Vault keys, deploy frontend. Do not rotate VAPID keys without resubscribing existing devices.

Verification: unit tests for endpoint restrictions and service-worker display/navigation; rolled-back database tests for create/update/delete, timestamp-only suppression, queue routing and cross-user RLS; unauthenticated API rejection and public-key-only configuration; lint and production build. A physical iPhone opt-in and background receipt still require the owner to enable notifications on that device.

## ERP customization

`owner_push_preferences` stores one policy per business; only approved owners of that business may read/write it. Defaults preserve all operations/sections/branches. Owners can pause business notifications, edit title/body templates, choose action-label/date language (EN/AR/FA), filter operations and ERP sections, restrict branches, and hide the record reference variable. Supported variables: `{business}`, `{branch}`, `{action}`, `{entity}`, `{reference}`, `{time}`. Templates are plain text, not executable expressions or HTML. Record-type labels are humanized table names. Dates use the business timezone with Riyadh fallback.

Settings apply at delivery time, including queued/retried events. Paused or filtered deliveries become cancelled; resuming does not replay them. Activity history continues. Explicit tests bypass event filters/pause and render the saved template using a synthetic TEST-001 record; unsaved editor changes appear only in the preview. Branch filters match canonical branch IDs, legacy keys, or unambiguous names. With a branch restriction, branchless/unresolvable events are excluded. An empty branch list means all branches and business-wide records. Empty operation or section lists mean no business pushes. These settings do not change the device's permission or VAPID subscription.

The settings editor supports EN/AR/FA and shows validation, a live sample preview, save feedback, and a reset-to-defaults draft. Unit tests cover filters, privacy, literal substitution, branch ambiguity and template bounds. Rolled-back SQL tests verify owner upsert, cross-tenant read/write denial and invalid-template/module rejection.

### Daily financial layout

Owner push settings include a multilingual financial preset and editable `{sales}`, `{expenses}`, `{purchases}`, `{net_profit}`, `{date}` and `{currency}` fields. Default notifications show business, branch, reporting date, sales, expenses and net profit. Existing custom text is preserved; the enabled financial-summary switch appends the financial block when the body has no financial amount fields. Explicit amount tokens work even if automatic append is off.

Totals are a live snapshot of **today at delivery time**, in the business timezone, for the resolved event branch. They are not the amount of the individual changed record. Unresolved/business-wide events display `—` instead of guessing a branch. Currency comes from the business configuration. The test sends live totals; the settings preview is explicitly illustrative.

The service-role-only aggregation RPC uses finalized/locked restaurant daily sales, or posted/approved retail transactions (refunds and voids subtract). Purchases count approved supplier invoices once plus standalone purchase lines; linked invoice lines are excluded. Expenses include daily variable costs and the Closing-style daily allocation of fixed costs. Net profit follows ERP's purchase-based operating formula, not an inventory valuation/COGS calculation. No debt repayments or owner cash injections are revenue. Only approved owners receive delivery; branch and operation filters still apply. Financial data can appear on the device lock screen. OS notification presentation determines how many lines are visible without expanding.

The expanded financial preset includes approved purchases, network sales, POS sales and Sales Sources. These channel figures overlap and must not be added to total sales or used again in profit. Restaurant network = recorded network sales; POS = touch-POS receipts plus structured POS amounts on other finalized sales rows. Sales Sources uses only today's `amount`/`today_amount`, excludes `included_in_revenue:false`, and never sums historical previous/total values. Both JSON arrays and legacy JSON-encoded strings are supported. Retail POS uses the posted transaction total, signed card/mada/Apple Pay payments for network, and zero for Sales Sources because that ledger has no configured Sales Sources attribution. Stock templates are upgraded; custom owner text and filters remain unchanged.
