# Customer self-service portal

Customers open `/customer-portal`, sign in and activate an owner invitation bound to their verified email. Owners issue/reissue or revoke access from Customer Management → customer details. Creating another invitation replaces the previous link and revokes the previous identity binding. Links expire after seven days and are single use. Existing identities can accept an invitation without another registration. Identity-only signup reuses the existing people registration path; it does not create a staff membership.

The portal presents customer-linked orders and their line items, credit invoices, payment receipts, and canonical receivable totals. Date filters and pagination affect the activity list; totals remain explicitly all-time. The print action prints the visible page. Data refreshes every twenty seconds and on window focus. Multiple authorized accounts remain separate by customer ID and business currency. Financial corrections and payment posting remain business-controlled; this release does not implement online payment processing or let customers modify recorded balances.

Security: private security-definer implementations behind public invoker wrappers; explicit authenticated grants; caller identity checks; verified email invitation acceptance; owner-only invitation operations; no direct API grants on the access table. RLS with no policies on that table intentionally denies direct access. Statements enforce tenant, customer ID and branch before reading finance or order records and return only approved presentation columns, excluding passwords, internal notes and staff metadata. No matching by name/phone.

Validation: 15 focused Vitest tests pass, covering UI account switching, signout, denied/revoked access, registration metadata, invitation/revocation and existing customer finance behavior. Transactional SQL tests exercise real functions and authenticated roles with synthetic identities; fixtures roll back. They cover wrong/unverified email, expired/reused invitations, non-owner access, same-name customers, branch isolation, liability/write-off exclusion from totals, dates, paging, order details, payment history and revocation. Production build passes. Supabase security advisors report the intentionally locked access table as INFO (RLS without policies).

Limitations: historical transactions without an exact customer ID are excluded rather than attributed by name. Only the canonical orders table is used for purchases; anonymous/POS transactions that lack this relationship cannot appear. Full browser signup/email delivery and a physical mobile device session remain to be verified. No existing user record is removed by the migration.
